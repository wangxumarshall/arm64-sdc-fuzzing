# FARRON 3 小时 stress-ng 环境性能复测（2026-10-26）

**问题（用户）**：3h stress-ng 环境下 FARRON 测试：运行多少轮、检出多少次 SDC、FARRON CPU 消耗占总 CPU 消耗多少、吞吐占总吞吐多少、延迟如何。
**环境**：stress-ng v0.22.01，191 worker 满载于可靠池 0-178,180-191（排除 179）；FARRON 逐插槽独占轮扫（应用整插槽迁出 → 48 核 `neon_rot_ldr_at_top_rowmajor -T 30s` → 恢复），连续背靠背；风扇混合档（F1-3≈70%、F4-6=100%）；98°C 看门狗在岗；运行前实测空闲本底 busy 0.2%。
**新增测量**（相对 10-25 的 5h 评估）：全机总 CPU 采样（`/proc/stat` 聚合行，15s）+ 应用 CPU 采样（stress-ng 进程树 utime+stime，15s）→ 首次给出 FARRON 的 CPU 消耗占比分解。
**数据**：`farron/state/sweep/eval3h/`（sweeps.csv 351 窗、fail_times.csv 239 行、cpu_total.csv 741 样本、app_cpu.csv 705 样本、87 份 CPU4 检出窗 stdout、temp_5s.log 5s 级全程）。
**运行窗口**：09:07:38 → 12:07:52（10,814s，3h 整）。

## 一、核心答案

| 问题 | 结果 |
|---|---|

| FARRON CPU 消耗占总消耗 | **13.3%**（22.27 核 / 全机总消耗 166.97 核；扣监控本底后 ≈13.1%；占机器容量 11.6%） |
| 应用吞吐占总吞吐 | stress-ng 占总消耗 **86.7%**、占机器容量 75.4%；吞吐保持率（vs 自身 191 worker 满速）**75.75%**，损失 24.25% |

## 三、CPU 消耗分解（本日首次测量）

3h 全程（对齐窗 09:07:34→12:07:58，dt=10,824s，实测 USER_HZ≈100）：

| 消耗方 | 核数当量 | 占总消耗 | 占机器容量(192核) |
|---|---|---|---|
| stress-ng（应用） | 144.69 | **86.66%** | 75.36% |
| FARRON 测试进程 | 22.27 | **13.34%** | 11.60% |
| 监控/采样/系统本底 | ≈0.3-0.4 | ≈0.2% | ≈0.2% |
| 全机 busy 合计 | 166.97 | 100% | **86.9%**（≈25 核当量空闲） |

**可信度交叉验证**：应用侧理论预测 = 144 核×98.6%（窗口期 REST 掩码恒为 144 核）+ 191 核×1.4%（窗口间隙）= 144.6 核，实测 144.69——完美吻合，应用数字可靠；FARRON = 总账 − 应用，随之成立。

**窗口归因**（15s 采样按窗口类型分桶，n=713）：

| 窗口类型 | busy 均值 | 测试进程占用（占 48 核预留） |
|---|---|---|
| CPU1/2/3 干净窗 | 162.0-163.6 | **~17.3-18.9 核（≈37%）** |
| CPU4 检出窗 | 178.8 | **~34.1 核（≈71%）** |
| 四类按窗数加权 | — | 22.3 核 ≈ 总账 22.27（自洽） |

**机制（源码定位，`framework/sandstone_run.cpp:1664-1817`）**：测试通过时以 fracture 分段模式执行——每段 ~40 次迭代后主线程做日志/种子推进/温度打印等记账，期间 48 个测试线程在 futex 上等待（核空闲）→ 干净窗占空仅 ~37%；**失败后的重试轮显式禁用 fracture（`current_max_loop_count = -1`）满速跑** → 检出窗占空 ~71%。空闲机单窗逐秒形状探针因会话工具限制当日未能执行，机制结论依据 = 源码路径 + 窗口归因 + 总账三方一致。

**含义**：FARRON 的真实 CPU 成本（13.3%）远低于其预留的插槽容量（48/192=25%）。背靠背连续轮扫协议下机器有 ~11% 容量处于"被预留但测试未用"的空闲态；生产节奏（每 30min 一轮 ~2.2min 扫描）下该空闲自然消失。

## 四、吞吐

- **应用吞吐保持率 75.75%**（实测 144.69 核当量 / 191 worker 理论满速），损失 24.25%——与 5h 基线 76.0% 一致。
- 损失主因是**结构性**的：连续背靠背协议下 98.6% 的时间里总有一个插槽（48 核）被整体让给 FARRON，应用恒运行于 144/191 核；其中仅 ~13 个百分点被 FARRON 真实消耗，其余 ~11 个百分点是预留插槽空闲。
- 生产节奏推算（每 30min 一轮 2.2min 扫描）：损失 ~1.8%（同 5h 报告口径）。

## 八、结论

1. 检出能力稳定复现：100% 窗口检出、零误报、全部锁定 179——FARRON 在 stress-ng 满载环境下 118s 端到端抓到缺陷核，检测延迟中位 15.9s。
2. FARRON 真实 CPU 消耗仅占总消耗 **13.3%**（22.3 核当量）；应用吞吐保持 **75.75%**。损失的大头是连续轮扫协议的插槽预留（结构性 ~11% 容量空闲），不是测试本身的计算。
3. 附带发现：opendcdiag fracture 分段机制使干净窗测试占空仅 ~37%（段间主线程记账时测试线程空闲）——若未来要压低 FARRON 预留成本，可研究跳过段间记账或降低 fracture 频率的配置；但需注意 fracture 每段推进随机种子，对检出率或有贡献，改动前须 A/B 验证。
