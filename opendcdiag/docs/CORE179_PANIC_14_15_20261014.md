# CORE179 第14/15次内核panic —— neon_rot_ldr_at_top_rowmajor 30min 运行中两次重启（2026-10-14）

## 结论

2026-10-14 上午 `./builddir/opendcdiag -e neon_rot_ldr_at_top_rowmajor -T 30min` 运行期间的两次"重启"，实为**两次 CPU 179 内核 panic**：Oops → `panic_on_oops=1` → panic → kdump 抓取 → 转储完成后自动重启。两次的致命位置与此前 13 次**逐指令相同**：`find_busiest_group+0x140`（机器码 `f9409377`，即 `ldr x23,[x27,#0x120]` 读 per-CPU runqueue 统计），构成 179 panic 序列的**第 14、15 次**。

- 根因不变：**179 硅故障在内核态的投影**（load 路径随机错值 → 组装出非规范地址 → translation fault）。见 docs/CORE179_PANIC_ROOT_CAUSE_SCHEDULER_FINDING_20260912.md。
- neon_rot_ldr_at_top_rowmajor 全核负载是**触发条件**（179 当时在线、sar 证实有负载），不是新增诱因。本次未按冒烟规范先 hotplug 下线 179。
- 测试两次分别只存活约 4~5 分钟和 ≤4 分钟，均远未到 30min；测试自身无持久日志（命令未带 `-o`，stdout 随 panic 丢失）。
- "机器自己重启"的机制 = kdump 流程（转储完成 → 重启），非看门狗、非人为断电（BMC watchdog Stopped/No action，sbsa_gwdt inactive，wtmp 两次均标 `crash`）。

## 3. 前兆串：52 条 WARNING 无一例外落在 CPU 179（10-08 起，新证据）

- boot #1（10-03 16:33 ~ 10-14 10:11）的 vmcore-dmesg 与 /var/log/messages 均记录 **52 条** `Ignoring spurious kernel translation fault` + `WARNING: CPU: 179`（`arch/arm64/mm/fault.c:494 __do_kernel_fault`）；按 CPU 统计 WARNING 总数**只有 CPU 179 一行 = 52**，其他 191 核零条。
- 栈全部相同：`el0_svc(read) → vfs_read → seq_read_iter → show_interrupts → seq_printf → __memcpy → translation fault`。受害者均为 /proc 读取者：pmdalinux(PID 10378)、irqbalance(PID 9694)、bash 一例（10-13 17:19，地址 ffff202297e7b518）。
- 坏地址高度聚类：ffff604befce943a/9419/94ea/9516/95c6/973c/e6ce/ec6a2/ef31c/ef3ab…（同一 ~24KB 内核地址邻域），另有 ffff6040…/ffff6020… 散例——规范内核地址上的"伪"翻译错误（页表复走有效→kernel 判 spurious 并忽略+WARN），与 runqueue panic（读 `__per_cpu_offset[]` 得垃圾→组装非规范地址）同属 179 load 路径随机错值的内核态投影。
- 时间分布与负载日强相关：10-08（白天密集爆发）、10-09、10-13（pcp-pmie 记录 93%util）、10-14；静默期零条。
- 今天 10:06:27 起爆发 5 条（含 40ms 内 3 连发），最后一条后 **9 秒**即致命。
- 注意：boot #2 的 panic（存活 442s）**没有任何 WARNING 前奏**——全新内核下负载启动数分钟内即可直接致命，WARNING 串非必要条件。

## 4. 179 在线状态与负载

- `sar -P 179`：10:00:01–10:10:39 窗口 CPU 179 在线且 26.6% user / 73.15% idle —— **测试期间 179 在线**（若已 hotplug 下线则 /proc/stat 无该行）。按冒烟规范应先下线 179（本次未执行）。
- `sar -u` 全局同窗口均值 27.14% user（10 分钟窗内测试仅占部分时间；测试实际启动 ~10:06–10:08）。boot #2 期间无 sar 采样存活。
- 两次 panic 的受害进程都是系统守护进程（sshd/jbd2），说明触发不依赖测试线程本身踏上 179——全核负载抬高 179 上的调度流量即足够（与 09-12 复现推论一致）。

## 5. 排除项

| 假设 | 排除依据 |
|---|---|
| BMC 看门狗复位 | `ipmitool mc watchdog get`：Stopped / No action / 0x00 |
| SoC 硬件看门狗 | sbsa_gwdt state=inactive（未启用） |
| 人为/计划内重启 | wtmp 两次会话均标 `crash`（非 clean shutdown）；messages 无 shutdown/reboot 序列，直接静默后接 boot banner |
| panic 挂死被人为断电 | kdump 目录时间戳（10:12:13 / 10:30:26）与死亡窗口精确吻合、转储完成 mtime（10:18 / 10:33）后约 4 分钟 boot——完整 kdump 抓取→重启流程 |
| 软件变更 | 今日无 dnf 事务（10-10 21:44 装过 rasdaemon，与本次无关）；内核版本 6.6.0-145.3.23.154 未变 |
| 测试程序直接导致 | opendcdiag 是用户态测试；两次 Oops 都在内核调度器路径、受害者是无关守护进程；neon_rot 家族历史上多次全核运行，panic 机理与 09-12 第 11 例（同族测试运行中 panic）一致 |

**pstore 为空的解释**：后端为 erst；kdump 激活时 panic 路径先 crash_kexec 接管，pstore 写入不会发生——空 pstore 不构成"没有 panic"的反证。

## 7. 建议与遗留

1. **跑全核测试若不以 179 SDC 为目标：先 hotplug 下线 179**（既定冒烟规范，本次未执行）。若以 179 SDC 为目标（如 neon_rot 家族），需接受 panic/重启风险——vmcore 会自动落盘，属既定代价。
2. 测试命令建议带 `-o <日志文件>`：stdout 随 panic 丢失，本次两次运行的测试侧输出（含 SDC fail 数据）全部丢失，只有内核侧证据存活。
3. 两个新 vmcore 若无需 crash 工具深挖（未闭环开口：确认 `__per_cpu_offset[cpu]` 内存值正确而寄存器读错），可保留 vmcore-dmesg.txt 后清理大文件。
4. **SEL 于今日 11:13:36 被清空**：11:05 首次读取时历史条目尚在（最后可读条目 10-09 22:16，其后条目读取报错 0x81，"Event Logging Disabled" 表明日志已停走多日）；清空后仅剩 2 条新事件。崩溃窗口的 BMC 侧证据缺失（不影响根因判定，vmcore 已闭环）。清空操作非本次分析会话所为（只执行过 sel list/sel info）；建议与当时在线的 root 会话确认，或排查 BMC "almost full" 自动清理策略。
5. WARNING 串（52 条全 179）是 10-08 起就存在的慢性内核侧信号，任意负载日都可能爆发；今日首次在 neon_rot 30min 场景下升级为双 panic。后续任何"机器重启了"事件可直接查 /home/sdc/vmcore/ 新目录 + /var/log/messages（sudo）+ /var/log/sa 采样缺失点，5 分钟内定性。
