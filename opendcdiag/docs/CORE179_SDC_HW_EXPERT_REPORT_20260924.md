## 摘要

一台 192 逻辑核心的鲲鹏 920 服务器（TaiShan V110 核心，ARMv8.1-A）上，逻辑核 179 存在静默数据损坏（SDC，Silent Data Corruption）：load 指令以极低概率返回错误数据，全程无机器检查异常（MCE）、无 RAS 计数、操作系统完全无感知。经过约两个月的受控实验，我们已经在软件层确认了以下事实，并在本文第四、五节列出目前无法用软件手段解释的现象，恳请硬件架构方面的分析支持。

已确认的核心事实：

1. 数千个出错样本 100% 落在核 179，其余 191 个核零错误；将 179 从操作系统调度中移除后，同等负载长时间运行完全干净。缺陷绑定该核心的硅。
2. 错误发生在 CPU 读取侧：内核崩溃瞬间的内存映像证明被读的内存内容完好，而寄存器中收到了来自错误位置的数据。
3. 错误不是随机位翻转，而是结构性的"数据错接"：错误值是工作集内其他 16 字节位置的逐字节副本，或符合一个确定的跨字段搬移公式；异或（eor）运算的结果从未出错。
4. 触发要求一组严格的指令级条件同时满足（第四节），其中多项条件指向 128 位 NEON 通路按 64 位 lane 消费数据的那一段路径。
5. 同一缺陷在内核态会引发致命崩溃：12 次内核 panic 全部崩在同一台核心（179）上执行的同一条调度器读指令。

## 一、环境与检测方法

- 平台：鲲鹏 920，TaiShan V110 核心（4 发射乱序，2 条 128 位 NEON 流水线，LSU 为 2 个 load AGU + 1 个 store AGU，L1D 64 KB 4 路组相联，实测主频约 2.35 GHz），192 逻辑核（8 个 NUMA 节点 × 24 核），openEuler，Linux 6.6。
- 核 179 的物理位置：NUMA 节点 7，module 23340；176–179 四个核心共享同一个 L2（此拓扑由 sysfs 在 179 下线时的报告中确认）。
- 检测工具：OpenDCDiag（开源 CPU 诊断框架）的 ARM64 移植版。测试在内层循环中对数据做"黄金参照值"比对（golden comparison），结果不符即记一次失败事件（fail block）。所有正式测量均为：192 个线程占用全部 192 个逻辑核心（含 179）、每轮 30 分钟、随机数种子每轮自动更换、日志完整落盘。失败核心号通过日志中的线程号与 192 位 CPU 掩码双重确认。
- 判定一个测试"有效"的标准：在上述条件下触发过至少一次失败事件，且失败全部锁定核 179、其余 191 核零错误，并有可追溯的日志证据。

## 二、有效测试用例

### 2.1 总量与分组

全项目共 **57 个唯一注册的测试名**确认触发过核 179 的 SDC，按研发阶段分五组（完整清单见附录 A）。按触发能力分层：

| 层 | 测试 | 典型触发率（次/30 分钟） |
|---|---|---|
| 最高且稳定 | `neon_rot_ldr_at_top_rowmajor` | 七轮平均约 255，最高 320 |
| 高 | `neon_rot_ldr_at_top_sub`（90–138）、`neon_rot_ldr_at_top_str3`（49–164）、K-cells 七用例（8–78） | 50–160 |
| 中 | `mrn_reloaded_2src_alu`（126/36 分钟）、`neon_rot_2src`（26–33）、`movbe`（57）、`agu_stress_2src`（19） | 15–130 |
| 低/间歇 | `mrn_rmw` 系（1–11）、`eigen` 系（1–44，需长跑）、各类探针（1/10 种子级别） | 1–44 |

另有 4 类"零触发"对照变体（附录 B），它们与触发用例只差一个条件，是第四节各条结论的反面证据。

### 2.2 最有效的测试用例：`neon_rot_ldr_at_top_rowmajor`

在所有受控测试中触发率最高且长期可复现的是 `neon_rot_ldr_at_top_rowmajor`。2026-09-08 至 09-11 的七轮完整 30 分钟测量结果为 309 / 276 / 244 / 149 / 271 / 216 / 320 次失败，平均约 255 次/30 分钟（约 8.5 次/分钟），最低一轮也有 149 次；全部失败 100% 落在核 179（2026-09-09 一次三变体各三轮的连续复测共 1019 个失败事件，逐条核对无一例外）。失败时间在 30 分钟窗口内均匀分布，不集中在开场；首例失败最短 6 秒出现。需要说明：09-13 之后同一测试的触发率明显下降（58/18/17 次），同一用例跨夜晚的这种整体波动本身也是尚未解释的现象之一（见 5.6 节）。

**它的测试负载：**

- 数据布局：4 个共享只读缓冲（srcA、srcB、scratch、expected）各 1024 个 16 字节元素（`uint64x2_t`，即 2 条 64 位 lane 的 NEON 向量），每个 16 KB，合计 64 KB 工作集——恰好等于 L1D 容量；另有每线程私有的 temp、dst 两个 16 KB 写缓冲。srcA/srcB/scratch 用随机数据填充（框架周期性重启测试时重新随机化）。
- 每个元素执行 3 次 16 字节向量 load（`ldr q`）+ 1 次 NEON 向量运算 + 2 次背靠背的 16 字节向量 store（`str q`）。
- 三次 load 中：第 1 次读 scratch，其结果在架构上不被任何后续指令使用（纯粹占用 load 端口，靠内联汇编阻止编译器删除）；第 2、3 次分别读 srcA[i] 和 srcB[i]，是运算的两个数据源。
- 向量运算按 `i % 4` 逐元素轮换：`vaddq_u64 / veorq_u64 / vandq_u64 / vorrq_u64`（即 `add v0.2d / eor v0.16b / and v0.16b / orr v0.16b`，按 64 位 lane 组织）。
- 扫描顺序：偶数轮从下标 0 升序扫到 1023，奇数轮降序扫回，交替进行。
- 校验在循环外的代码中做：每完成一遍 1024 元素的扫描，用 `memcmp` 将 dst 与 init 阶段预计算的 expected 逐字节比对；仅比对失败时才执行出错报告与数据快照写入，主循环内没有任何分支通向校验代码。

**主循环的实际机器指令序列**（对最终二进制反汇编逐条摘录，降序段；每个元素执行一遍，`i%4` 的分支体每次只走一条）：

```asm
; x19 = 指向 4 个缓冲区指针的结构体; x0 = 当前元素字节偏移
ldr  x1, [x19, #16]          ; 重新读取 scratch 基址
add  x1, x1, x0              ; 计算元素地址
ldr  q0, [x1]                ; ① 向量 load：scratch[i]（结果不被使用）
ldr  x1, [x19]               ; srcA 基址
add  x1, x1, x0
ldr  q0, [x1]                ; ② 向量 load：srcA[i]（数据源 A）
ldr  x1, [x19, #8]           ; srcB 基址
add  x1, x1, x0
ldr  q1, [x1]                ; ③ 向量 load：srcB[i]（数据源 B）
and  w1, w2, #0x3            ; i % 4
cmp  w1, #0x2 / #0x3 ...     ; 按余数跳到四条运算指令之一
add  v0.2d, v0.2d, v1.2d     ; ④ 四选一（同形还有 eor/and/orr v0.16b）
str  q0, [x21, x0]           ; ⑤ 写 temp[i]
str  q0, [x20, x0]           ;   写 dst[i]（与上一条背靠背）
sub  x0, x0, #0x10           ; 元素偏移前进 16 字节（降序）
cmn  x0, #0x10
b.ne <循环头>
```

从数据依赖看：② ③ 两条 load 的结果不经寄存器堆往返、以零延迟旁路直接供给运算指令④（load-to-use 旁路）；④ 的结果同样以零延迟旁路直接供给两条 store ⑤（运算结果到 store 数据的旁路）；① 的结果没有任何依赖边，只占用 load 端口与写回资源。主循环内没有任何一条活跃依赖边经过寄存器堆完成数据传递。

## 三、研究过程简述

**第一阶段（2026 年 8 月）：发现与定性。** 在全套件并发运行中偶然发现数据比对失败，随后确认所有失败都锁定核 179、每次错误翻转 10–39 位（无一例单位）、需要全核并发与随机输入才出现。定性为单核硬件缺陷，软件侧的任务转为"精确激活并刻画它"。

**第二阶段（09-01 至 09-04）：从两个触发测试提炼出触发条件。** 对 22 个既有测试逐一反汇编对比：只有 `movbe`（57 次/30 分钟）和 `mrn_rmw`（6 次）触发。关键反例是 `mrn_nuke`：它与 mrn_rmw 的"写后立即读回"两条指令逐条相同（同地址、同寄存器、零间隔），却不触发——两者唯一的可见差异是 mrn_rmw 在写入之前有两条源 load 和一条数据处理指令，而 mrn_nuke 只有一条源 load 且搬运原值。反汇编还修正了 movbe 的真实形态：它是**单源**测试——对同一个 input 地址连续两次 load（中间隔字节交换和一次对另一数组的写入），比较两次读到的值是否一致；它并没有第二条源 load。随后通过正向构造验证：把"两条源 load + 数据运算"加进 mrn_nuke 后立即触发（14 次/约 30 分钟）；移植到另外两个不触发的测试骨架上分别得到 46 次/36 分钟和 126 次/36 分钟。一对关键对照实验锁定了时序条件：两个变体指令内容完全相同，仅把"写入与读回"之间的间隔拉开 7 条指令，触发从 46 次降到 0。进一步的梯度实验给出：源 load 数 1/2/3/4 对应 0/14/10/4 次触发（2 源是峰值，不是越多越好）；把轮换的四种运算固定为任何单一指令（加、减、异或、与各跑 36 分钟）全部零触发——**必须是轮换的混合运算**。

**第三阶段（09-05 至 09-12）：收敛到当前骨架。** 把上述条件组合搬进 NEON 向量通路并做 lane 形状对比后（结果见 5.5 节），形成了第二节描述的"3 条 load + 轮换 NEON 运算 + 2 条 store"主循环，并以交替扫描顺序得到最高且最稳定的触发率。同一时期确认了该缺陷在内核态的显形（见 4.5 节）。

**第四阶段（09-13 至 09-16）：错误形态取证。** 给每个数据字编码来源信息（16 位 magic 标识缓冲身份 + 字节偏移 + 偏移反码，使每个捕获的错误自动报告"它的字节从哪里来"），在指令序列完全不变的前提下获得大批量带来源信息的错误样本，得到第四节 4.3 的错误形态结论。目前固化的 7 个主力检测用例（K-cells 七用例）即来自这一阶段，两晚复测 7/7 全部复现。

## 四、已确认的结论与最直接的证据

### 4.1 缺陷绑定核 179 的硅

- 全部历史实验中数千个失败事件，失败核心号 100% 为 179（三重核对：日志线程号、192 位 CPU 掩码中唯一置位、崩溃转储的 CPU 字段），无一例扩散到其他 191 核。
- 用 hotplug 将 179 从操作系统调度中移除后，同等满负载长时间运行零失败、零内核错误。
- 相邻的 180 核对照：3 小时满载，访客进程在 179 上到访两千余次无一死亡、内核零错误，而同期用户态错误 113 次全部在 179——错在核，不在进程。

### 4.2 错误在 CPU 读取侧，不在内存或缓存中的数据

用 crash 工具直接读取内核崩溃瞬间的内存映像：被读数组 `__per_cpu_offset[]` 的内容完全健康（数值步进规整、无垃圾），而寄存器 x20 中的值是同一数组基址 +19 至 +26 字节处 8 个字节的逐字节副本——与正确值相差 141 字节、跨缓存组、字节错位 mod-8=3。内存对、寄存器错。用户态侧同样用"在健康核上重算黄金参照值"排除过参照值本身算错的可能。

### 4.3 错误形态：结构性的数据错接，不是随机位翻转

这是目前信息量最大的一组结论，来自约 500 个出错数据快照、上千个出错字的逐字节溯源（每个出错字都能在工作集快照中检索其真实来源）：

1. **错误值是工作集内既有数据的逐字节副本。** 最新一轮（dualcmp 变体，2026-09-16，三轮 33 个错误元素）100% 可在工作集中寻回错误值的来源，0 例不可溯源。其中 15 例：dst[j] 的 16 字节内容 = 预期结果缓冲中 exp[k] 的完整 16 字节，k−j 为 ±8/±12/−16 个元素（±128/±192/±256 字节，全部是 64 字节缓存行的整数倍）；15/15 保持 k≡j (mod 4)——错的地址仍落在与受害者相同的运算轮换槽位上；15/15 与扫描方向强相关（升序扫描时来源在受害者前方，降序时在后方）。另 9 例是一条起点非 16 字节对齐的连续 16 字节损坏窗，跨越两个相邻元素，内容同样来自预期结果缓冲的远处位置。**同一元素的两条 store 中，第一条（写 temp）在全部 33 例中零错误，错误只出现在第二条（写 dst）的数据上。**
2. **跨字段搬移公式。** 带来源标签的批次（386 个快照、861 个出错字）中最大的一类错误精确符合 `错误值 = 正确值 ± X·(2³²−2¹⁶)`（294/294 例，100% 符合）——即 64 位字内两个 16 位字段之间发生了一笔幅度为 X 的"借位/进位记账"。X 集中在 0x80（44%）、0xc0（22%）、0x100（11%）等固定量级。
3. **运算类型偏置：异或几乎完全免疫。** 两批独立测量结论一致。第一批 156 个出错字：orr 110 个（71%）、and 36 个（23%）、eor 仅 8 个、add 2 个；第二批 294 个出错字：orr 186 个、and 68 个、add 40 个、**eor 0 个**。如果缺陷是数据传输线上的位翻转，四种运算的错误率应当接近——eor 的输出与输入是逐位异或关系，任何位翻转都会直接暴露；它几乎不出错，说明错误发生在"选择/装配哪个数据"的一级，而不是数据在通路上被改变。
4. **错接数据的来源不跟随物理地址相邻。** 把两个源缓冲交错排列进同一地址空间（使每个地址邻居永远是另一个源）后，首轮占 93% 的"同缓冲近邻字段替换"错误形态消失，错误值在交错缓冲全表中 0/91 命中；最新一轮中近距错接的来源甚至是参照值缓冲——它在主循环中从不被访问，只被循环外的校验代码按遍读取。
5. **与内核崩溃签名一致。** 用户态错误中的 mod-8 字节错位窗形态，与 4.2 节内核崩溃寄存器中观测到的错位字节窗是同一种形态。

综合判断：损伤位于**地址捕获/数据装配级**——即决定"这次 load/store 取回或写入哪个数据"的那一环（含进位链形状的选择电路），而不是数据传输线本身。异或零出错 + X·(2³²−2¹⁶) 的搬移形状 + 错接值来自预期结果缓冲这三条证据共同指向这一级。

### 4.4 触发条件（每条均有"只差这一个条件的变体零触发"的反面证据）

| 条件 | 正面证据（触发） | 反面证据（去掉该条件 → 零触发） |
|---|---|---|
| 至少 2 条源 load + 数据运算依赖链 | 2 源骨架 14–126 次/36 分钟 | 单源变体（标量与 NEON 各测）均为 0 |
| 运算必须轮换/混合 | 4 种运算轮换触发 | 固定为任一单一运算（含纯 add、纯 eor）各 36 分钟均为 0 |
| load → 运算 → store 全链背靠背 | 零间隔触发 | 在 load 与运算之间插 8 条 nop，或在运算与 store 之间插 8 条 nop，均为 0 |
| 热循环内必须有 store | 2 条 store 触发（58 次/30 分钟） | 删除全部 store、用异或累加器消费结果（指令序列其余不变）：0 |
| 输入数据必须非均匀 | 随机/全 1/高翻转密度数据均触发 | 全 0 数据 30 分钟 0 触发 |
| 128 位 NEON 通路按 64 位 lane 消费 | 2×64 位 lane（v0.2d）触发率最高 | 见 5.5 节四点对比 |
| 系统级满载 | 192 核并发稳定触发 | 见 5.1 节 |

表中"必须有 store"一条需要补一个限定：**store 的数据被转发回 load 并不是必要条件**。不含任何读回指令的变体（两条 store 都直接写运算结果）仍然触发（标量 1 次、NEON 14 次/30 分钟），"写入后立即读回"的转发窗口约把触发率放大 20 倍——它是放大器，不是开关。

附带定量估计：满足全部条件后，单次 load 出错概率约 10⁻⁶ 量级（由两个测试的 load 流量与错误率独立推算，分别为 1.0×10⁻⁶ 与 2.6×10⁻⁶，同数量级）。

### 4.5 内核态显形：12 次致命崩溃全部同源

满负载运行期间机器共发生 12 次内核 panic（2026-09-04 至 09-14），对全部崩溃转储逐一分析：**12/12 崩溃点完全相同**——调度器负载均衡函数 `find_busiest_group+0x140` 中读取每 CPU 运行队列统计的 `ldr x23, [x27, #0x120]`（机器码 f9409377，全部样本一致），且全部发生在 CPU 179 上执行。受害进程横跨 8 种互不相干的进程（sftp 服务、监控守护、内核工作线程、测试线程自身），共性只有一个：它们恰好在 179 上触发了调度器的负载均衡。配合 45+ 例全部来自 179 的可恢复"虚假翻译错误"内核警告，以及 4.2 节的内存健康证明，结论是：**用户态 SDC、可恢复内核警告、致命 panic 是同一个读取侧缺陷按错误值落点不同而分级显形的三种形态**。将 179 下线是唯一被证实可靠的阻断手段（cpuset 无法阻止操作系统把守护进程调度上 179）。崩溃全部发生在满负载开始后 1~16 分钟内；满载不必然崩溃，但崩溃发生时机器必然处于满载状态。

## 五、软件层尚未解释的观察（请教重点）

以下现象都有可追溯的实测数据支撑，但我们无法用软件手段解释其微架构成因。每条附我们已排除的解释。

### 5.1 触发依赖系统级满载，单核运行永不触发

- 实测：单个进程绑定在 179 上运行测试（其他核空闲），无论跑多久均零触发；必须 192 个逻辑核同时满载。触发率随负载升高而升高。
- 一个重要的细化实验（OFHC，192 个各自绑定单核的独立进程同时满载）证明：**关键条件是系统级全核满载这一状态本身，与测试进程如何组织、绑定在哪些核无关。**
- 已排除：不是"测试必须多线程"（192 个单线程独立进程同时满载同样触发）；错误值全部可在测试自身的工作集内溯源，不是外来进程的数据。
- 请教：对一个核内的读取路径缺陷而言，"其余 191 个核同时满载"改变了什么？候选方向包括供电/电压降（di/dt）、频率状态、温度、共享末级缓存或互联的背景流量、以及这些因素对时序余量的影响。179 与 176–178 共享 L2，同集群邻居的负载是否参与也未知。我们缺少核心级的电压/频率/温度读数手段（IPMI 只有 socket 级温度，且监控期间该字段为空）。

### 5.2 触发依赖输入数据的位模式

- 实测：全 0 数据 30 分钟零触发（同条件下随机数据 78 次）；固定随机数种子时，10 个种子里约 1 个能触发、其余种子跑再久也为零（其中一个固定种子曾连续复现 11 次失败——说明不是"固定种子绝对不触发"，而是该种子产生的位模式恰好处于激活态）；每轮自动更换种子（即持续刷新位模式）是标准触发配置的组成部分。
- 对 42 个触发时刻输入值的逐位分析：触发与任何固定的 0/1 位模式无关（最偏的位也未达统计显著性）。
- 请教：这符合"特定 bit 序列落在缺陷物理位置才暴露"的模式敏感（pattern-sensitive）失效形态。2×64 位 lane 组织下的 16 字节数据中段（32 位偏移字段所在区域）是错误高发区，而全 0/全 1 的字段（magic 段）几乎不出错——这种"避开均匀段、集中在中段"的选择性指向什么物理机制（耦合、保持余量、还是装配电路的输入依赖）？

### 5.3 访存指令数量存在尖锐的边界

- 实测（在"3 条 load + 2 条 store"的主循环上做单变量增减）：增加第 3 条 store 仍强触发（133–164 次/30 分钟）；增加到第 4 条 store 后零触发。4 条 load 仍触发但触发率降至原来的 1/4–1/8；增加到第 5 条 load 后零触发。源 load 数 2→3→4 递减（14→10→4）。
- 请教：为什么在如此小的计数上出现从"稳定触发"到"完全不触发"的悬崖？数量增加同时改变了发射带宽占用、store buffer 占用与指令间时序距离，软件无法拆分这几者。这一边界对定位"哪一段时序/资源窗口被踩中"应该是有力的约束条件。

### 5.4 运算必须轮换；错误高度偏向 orr/and，异或免疫

- 实测：四种运算逐元素轮换时触发；固定为任何单一运算（加、减、异或、与，各 36 分钟）全部零触发——包括纯异或。而已捕获的错误中 orr 占 71%、and 占 23%、异或 0 例。
- 编译器把 `switch(i%4)` 生成为"多条运算都执行 + 比较与条件选择指令挑结果"，所以硬件实际经历的是：产出 store 数据的依赖链深度以 4 为周期在 1/2/5 级之间变化，且加法器入口与逻辑单元入口交替。
- 请教：轮换的必要性是否说明缺陷窗口只在这类"依赖链深度/来源周期性变化"的调度形态下被踩中？orr/and 高发而 eor 免疫、加上 X·(2³²−2¹⁶) 的跨字段搬移形状，我们猜测与按 64 位 lane 组织的运算结果装配/选择电路（含进位链）有关——恳请从运算单元与结果选择网络的角度分析这个偏置。

### 5.5 强烈绑定"128 位 NEON 通路按 64 位 lane 消费数据"

- 同一主循环、同一指令位置，只换消费 load 结果的运算形态：2×64 位 lane（`add v0.2d` 等）触发率最高（26–320 次/30 分钟）；**4×32 位 lane（`add v0.4s`）零触发**（1651 轮完整通过）；16×8 位 lane（`.16b`）仅 2 次（塌缩约 15 倍）；**标量 64 位直译版零触发**（且标量版迭代速度反而快 4 倍，排除样本量不足）。
- 但标量路径并非完全免疫：在带"写入后立即读回"的另一套骨架里，标量 64 位测试能以低约一个数量级的频率触发（19、14 次/30 分钟）。
- 请教：哪一段物理路径是"128 位向量 load 的结果按 64 位 lane 供给向量运算"所独有、而 4×32 位 lane 消费、16×8 位消费、以及本骨架下的标量 64 位消费都不经过（或形态不同）的？NEON 寄存器堆的写端口与按 lane 的旁路网络是我们的第一怀疑对象，但没有手段直接观测。

### 5.6 触发率存在跨夜晚的整体波动

- 同一测试、同一二进制、同一运行配置：09-08 至 09-11 七轮 149–320 次/30 分钟，09-13 之后降至 58/18/17 次；七个主力用例某夜整体复测时 7/7 全部下降到前一晚的 45%（同向变化，纯噪声的概率约 1.6%），但用例之间的相对排序两晚保持一致。
- 已排除：执行顺序（逆序复测过）、迭代速度（两晚各用例迭代数相差 ±1%）。
- 未测：核心级温度与频率在整个实验期间没有可用读数，这是当前最大的未测量变量。请教：这台机器上是否有可用的核心级传感器（温度/电压/频率）通道可以推荐接入？

## 六、需要硬件架构方面的支持

### 6.1 直接问题：第二节描述的负载涉及哪些 CPU 内部单元

按指令序列，我们理解该主循环压到以下单元（恳请确认、补充或纠正）：

1. **load 流水线与 LSU**：每元素 3 条 128 位 load（其中 1 条结果无人消费、纯占端口）；
2. **AGU**：每元素 3 次基址重读 + 地址加法；
3. **NEON 寄存器堆的写端口与 load-to-use 旁路网络**：两条源 load 的结果零延迟直供向量运算；
4. **向量运算单元**：64 位 lane 组织的加法（2 条独立 64 位进位链）与按位逻辑运算，每元素切换入口；
5. **运算结果到 store 数据的旁路与 store buffer**：运算结果零延迟直供两条背靠背 store，不经过寄存器堆；
6. **L1D**：64 KB 工作集恰好压满容量，交替升序/降序扫描；
7. **调度/发射**：轮换分支 + 依赖链深度周期性变化。

我们做过的单元排除尝试及其局限：构造过分别压 TLB/页表遍历、LSQ 深度、寄存器堆端口、ROB 窗口、预取器的变体（PMU 计数确认 TLB 与预取器两个变体的压力确实生效），全部零触发——但每个变体都不可避免地改变了主循环的指令布局，而该缺陷对指令布局极度敏感，所以这些零触发无法区分"该单元不参与"与"布局改变使触发消失"（此局限对 TLB 与预取器两个变体较弱，因为其压力经 PMU 确认真实生效）。布局敏感的程度可以量化：仅在循环外增加一段只在比对失败时才执行的落盘代码（正常运行时从不执行），触发率即下降约 30 倍——这段代码的存在本身改变了整个函数的编译结果。

### 6.2 具体求助清单

1. **内部错误检测通道**：错误发生时无 MCE、无 RAS 计数。TaiShan V110 的 L1D/LSU 是否有可读出的 ECC 或内建自检（BIST）计数器？如果有，提供一个不经软件扰动 CPU 的读取通道，将是确认"错误产生于哪一级"的最干净手段。
2. **对 4.3 节错误形态的微架构解读**：X·(2³²−2¹⁶) 的跨字段搬移量（X 集中在 0x80/0xc0/0x100）、eor 免疫、mod-4 槽位保持、方向相关性——这一组签名对应哪一级的什么结构（进位链？字节使能生成？结果选择多路器？store 数据装配？）。
3. **满载条件的解释方向**（5.1 节）：电压/频率/温度/共享资源中，哪一项最可能解释"其余核满载才能触发单核读取错误"？该平台是否有可用的核心级传感器与 PMU 事件（尤其电压降、电源噪声相关）？
4. **lane 绑定**（5.5 节）：128 位 NEON 数据通路中按 64 位 lane 组织的段与按 32/8 位组织的段在物理上的差别。
5. **不改变指令布局的单元加压手段**：例如通过系统配置（预取器开关、频率锁定）或邻核放置背景负载的方式制造单元压力，绕开"改一条指令就可能使触发消失"的死结。
6. **179 的硅位置与已知问题**：NUMA 节点 7、module 23340、与 176–178 共享 L2。该批次/步进是否有已知的类似勘误（errata）？同一物理位置在硅片版图上的坐标能否从现有信息推出？
7. **复现支持**：如需现场复现，179 在线 + 全核满载 + 第二节用例即可在分钟级出错误（约 1–8 次/分钟量级）；我们可提供全部测试二进制、脚本与历史出错数据快照。
