# CORE179 SDC 物理层假说:涉及指令与可疑功能单元

**文档日期:** 2026-08-06(2026-08-07 修订:加一致性声明、更正指令描述)
**定位:** 本文是 [CORE179_SDC_ROOTCAUSE_REPORT.md](CORE179_SDC_ROOTCAUSE_REPORT.md) 的**物理层假说补充**。

> **⚠️ 一致性声明(重要):** 本文为**早期物理层推测**(di/dt 电压瞬态、供电网络、功能单元级损伤),写于根因尚未微架构定位之前。**最终微架构根因见主报告 §11.2** —— 经六层假设排除,故障定位在**乱序执行引擎的状态泄漏**(物理寄存器重命名/ROB/store buffer),而非任何执行单元本身或供电层。两者不矛盾:本文提供**物理诱发因素**(为何稀疏矩阵负载能激发缺陷),主报告提供**微架构定位**(缺陷在哪条写回路径)。引用本文结论时,请同时引用主报告 §11.2 的最终根因。

## 一、 `eigen_sparse` 的计算特征

192 核 ARM64 服务器上,单核(Core 179)在运行 OpenDCDiag 的 `eigen_sparse` 时爆出 SDC(Silent Data Corruption,静默数据损坏)。`eigen_sparse` 是专门用来"榨取"和暴露芯片微小物理缺陷(Marginal Defects)的测试用例,底层调 Eigen C++ 线性代数核心库:

1. **构造**:随机生成双精度实数的稀疏矩阵(256×256,CSR/CSC 压缩格式);
2. **计算**:通过直接法(Sparse Cholesky: `SimplicialCholesky`)求解线性方程组 `Ax = b`;
3. **循环验证**:将结果与 golden 比对,浮点尾数不匹配即抛失败,捕捉 SDC。

## 二、 为何"稀疏矩阵"能抓到 SDC(物理诱发因素)

密集矩阵(如 `eigen_gemm`)对 CPU 的压榨是"平稳的极高负载",而**稀疏矩阵测试是"脉冲式的极端电磨损"测试**:

* **极端的 di/dt 电压瞬态突变**:稀疏矩阵计算具有高度的**非连续内存访问**(Irregular Memory Access)。CPU 状态高频切换:
  * *状态 A(内存等待)*:找不到下一个非零元素,Cache Miss,流水线停顿;
  * *状态 B(满载计算)*:数据到达,所有浮点乘加单元瞬间满负荷启动。
* 高频"启-停-启"在极短周期内造成剧烈电流突变(di/dt)。
* **物理缺陷暴露**:当电流瞬间飙升时,Core 179 局部的供电网络(PDN)无法瞬间补偿,导致**局部电压骤降(Voltage Droop)**。若 Core 179 本身存在微弱的硅片工艺边缘缺陷(弱体质核),电压骤降会导致晶体管翻转延迟增加,从而在时钟沿到来时锁存错误数据位,而硬件校验纠错单元(ECC/Parity)又无法覆盖纯算术单元逻辑,最终酿成 SDC。

> **与主报告的关系:** 这一 di/dt 假说解释了"为何稀疏 + 满载"是物理诱发条件;主报告 §11.2 进一步把缺陷定位到**乱序执行引擎的状态泄漏**(而非供电层本身),即电压瞬态只是"放大镜",真正的损伤点是 OoO engine 的写回/状态管理路径。

## 三、 涉及的核心指令

> **⚠️ 更正(2026-08-07):** 本文早期推测 Eigen 在 ARM64 用 SIMD 向量化(FMADD/FMLA/LD1/SVE Gather-Load)。但经对 `esdiag_phase2` 编译产物的反汇编核查,`factorize_preordered` 热循环使用的是**标量**双精度指令(`fmsub d0, d1, d2, d0` 等 d 寄存器),**未使用 NEON 向量指令**(无 q/v 寄存器、无 LD1/ST1/SVE)。故下方"SIMD FMADD/FMLA"段为未验证的早期推测,实际触发指令是**标量 fmsub + 间接寻址 ldr/str**(见主报告 §10.4、§11.2)。原文保留以记录推测演进,但请以主报告 §11.2 的反汇编结论为准。

Eigen 库在 ARM64 平台的指令使用(含早期推测与反汇编更正):

1. **浮点乘加指令(触发主力,经反汇编为标量)**:
   * 实际:`fmsub d, d, d, d`(`SimplicialCholesky::factorize()` 列更新 rank-1 update,标量双精度,经反汇编确认);
   * 早期推测:SIMD `FMADD`/`FMLA`(Fused Multiply-Add),占用核心内部面积最大、功耗最高的浮点运算阵列——**未被反汇编证实,实际为标量**。

2. **非连续内存加载/存储指令(打乱缓存)**:
   * 实际:标量 `ldr d, [x, x, lsl #3]` / `str d, [x, x, lsl #3]`(间接索引移位寻址,经反汇编确认);
   * 早期推测:`LDP`(Load Pair)、`LD1`(Load Multiple Single-element Structures)搬运到 V 寄存器;支持 SVE 时调用 Gather-Load `GLD1D`——**未被反汇编证实**。

3. **地址生成与分支控制指令(打乱分支预测器)**:
   * `ADD`、`LSL`(逻辑左移)等用于计算 `row_ptr`/`col_idx` 指针(经反汇编确认);
   * 稀疏内积/列更新存在循环边界,频繁 `B.cond`(条件分支)。

## 四、 CPU 微架构逻辑单元(可疑点)

> **⚠️ 与主报告的关系:** 本节列出的"可疑功能单元"是早期推测。主报告 §11.2 的最终结论是:cache/TLB/分支/内存子系统/FPU pipe 在 per-core PMU 下**全部正常**,故障在**乱序执行引擎的状态管理**(物理寄存器重命名/ROB/LSU store buffer),而非下列任一执行单元本身。本节保留作为设计参考。

在 Core 179 内部,早期推测可能引发 SDC 的物理故障点:

#### 1. FMA Pipelines(浮点乘加流水线)
现代 ARM 核心通常有多条 128-bit 宽的 Advanced SIMD 流水线。推测 SDC 可能发生在乘法结果输入到加法归约器(Adder Tree)的最后一级,瞬态电压不够时进位链(Carry Chain)未跑完,导致双精度浮点尾数(Mantissa)差几个 bit。
> **主报告更正:** 纯 FMA 探针(`fma_probe.c`)0 触发,密集 GEMM/SVD 0 失败 → 排除"浮点 pipe 损坏"。实际触发需 rank-1 update 的间接寻址 + 长存活累加器交错,非单纯 FMA。

#### 2. LSU(Load/Store Unit,加载存储单元)
稀疏矩阵导致大量地址不连续,LSU 的 Load Buffer、Store Buffer 处于极度不平衡状态,经常被塞满或触发数据重放(Replay)。复杂的交错数据依赖可能在微秒级乱序执行(OoO)重排中诱发难以察觉的时序错误。
> **主报告关联:** 这与最终根因"乱序执行引擎状态泄漏"部分吻合——LSU store buffer 是三个可疑泄漏点之一(另两个:物理寄存器重命名表、ROB)。

#### 3. L1 D-Cache & D-TLB
访问跳跃(CSR/CSC 跨行读取),L1 数据缓存发生严重的组冲突(Bank Conflicts),数据 TLB 因频繁跨页被击穿。
> **主报告更正:** per-core PMU 显示核 179 的 L1D/dTLB refill 与健康核 176 差异 < 2% → 排除 L1D/TLB 损坏。差分 perf 显示 Eigen 的 L1D-refill 是纯 C 的 4.05×,但纯 C 探针匹配该特征后仍 0 触发 → L1D 压力非充分条件。

#### 4. 局部时钟树与电压稳压器(Local Clock Tree & LDO)
SDC 表面是计算错误,本质可能是供电错误。多核架构(192 核)中,全局供电不可能完全均匀。Core 179 可能位于 Die 边缘或靠近发热大户,其局部电压供应响应速度(LDO 或 PDN)慢了纳秒级别。
> **主报告关联:** 这一供电层假说未被排除(也无法在软件层证伪),与微架构根因并存:供电瞬态是诱发因素,OoO engine 状态泄漏是损伤点。最终确认需 RTL 仿真或芯片内部文档(主报告 §15.1 局限)。
