## 一、一页速览

- **FARRON 是什么**：在线 CPU 健康管理系统——业务不停机的前提下定期给全部核心做"体检"，抓静默数据损坏（SDC）核
- **本机场景**：stress-ng 191 个满载 worker 占满全机（模拟生产业务），179 号核有 SDC 缺陷（计算结果偶尔静默错一位，不崩溃不报错）
- **为什么是这台机器**：fleet 层日志分级命中 1/2/3/4/6（等级很高）——静默签名（软错+硬零报）+ 错误 100% 集中于物理核 179 + 30 天内多次非计划重启
- **三个大数字**：**100% 检出**（12/12 轮，全锁 179，零误报）｜业务吞吐损失 **1.815%**｜系统消耗 **0.88%**
- **一句话**：业务一秒不停，每 30 分钟花 2 分钟，把整机 192 核体检一遍——缺陷核每轮必中

## 二、设计概要（两页讲完）

### 2.0 前置：机器级日志分级筛查（fleet 层，运行 FARRON 之前）

不是每台机器都上 SDC 检测——先用日志特征分级筛选：

| # | 判据 | 效果 |
|---|---|---|
| 1 | 没有硬件报错信息 | 与软错并存的 SDC 静默签名 |
| 2 | 被 SDC 测试套件标记 | **直接最高级**（无论有无 SEL 报错） |
| 3 | ≥2 种应用软件报错 + 60% 以上集中于一个物理核 | 概率 ×10 |
| 4 | 30 天内 ≥3 次非计划重启 | 概率 ×10 |
| 5 | 多次送修未定位 | 概率 ×10（现无此情况——直接换板） |
| 6 | 软件错误总数前 N 台（暂定 N=50） | 嫌疑机器入围 |

**执行规则**：等级 ≥2 → 上 SDC 检测；命中 1+3 → 重点审核故障节点；≥2 不含 3 → 尽量多核测试。

**本机命中 1/2/3/4/6——等级很高**：① 15 天硬件错误报告全零 ✓ ② 套件 8000+ 事件 ✓ ③ 报错 ≥2 种、**100% 集中于物理核 179**（门槛 60%）✓ ④ 9 月任意 30 天窗重启 ≥3 ✓ ⑥ 软件错误总数顶尖 ✓

**实验修正注**（重要）："重点审核故障节点"不能做成只测嫌疑核——单核独占 330s 零检出（负载门控）；正确做法是**嫌疑核所在插槽整插槽独占并发深测**（FARRON 生产形态）。

### 2.1 状态机——"户口管理"

```
可靠资源池（应用只跑在池内核上）
   ↓ 每30min在线体检
在线状态（发现异常→该核进可疑队列）
   ↓
可疑状态（最强用例钉核深测复核，600s/用例×≤8）
   ↓
健康裁决：该CPU缺陷核 <2 → 屏蔽该核，其余回池
          该CPU缺陷核 ≥2 → 整颗CPU退役
```

### 2.2 三通道入口 + 配套

- **被动通道**：内核日志指纹（`WARNING: CPU: 179` 每核≥3条直送可疑队列）——加速器，不能当主渠道（469 次出错仅 22 次泄漏到日志）
- **主动通道**：定期测试——**主力**，即下文核心章
- **应用上报**：应用自发现异常写 `anomaly_<核号>`，即触即读
- 配套：温度控制器（热裕量自适应测试时长 300/120/60s）+ 三级用例池（可疑级 > 活跃级 57 个已证实检测器 P0-P4 > 基础级 83 个对照）

## 三、核心章：在线检测如何运行——满载下不停机、2 分钟完成全机体检

### 3.1 难题

stress-ng 把 191 个核全部占满。检测 179 这类 SDC 缺陷需要让被测核跑"高压陷阱"测试——**怎么在不打断业务的情况下让测试跑起来，并且测得又快又准？**

### 3.2 机制："借，不抢"

FARRON 从不与业务争抢 CPU，也从不暂停/杀死任何业务进程：

```
测 CPU4 的 30 秒里：
  ① CPU4 上的 ~48 个 stress-ng worker 被 taskset 整体迁到另外三颗 CPU
     （改亲和性，毫秒级完成；进程继续跑，只是换地方——"搬，不是停"）
  ② 测试进程的 48 线程一一钉上 CPU4 的 48 个空核，跑 30 秒
  ③ 30 秒到，业务迁回原核，测试退出
```

**业务视角**：任何时刻都保有 3 颗 CPU（144 核）在跑；被借的那颗上的 worker 降到 75% 速度 30 秒。**没有一秒停机，没有一个进程被杀。**

### 3.3 时间账：为什么"快"

| 层级 | 时长 |
|---|---|
| **全机一次完整体检** = 一轮（4 颗 CPU 各 30s 窗，背靠背） | **~2 分钟** |
| 单核被占用 | 30s / 每 30min = **1.67%**（实际计算 ~15s） |
| 端到端首检（系统启动→第一次抓到 179） | **124 秒**（首轮扫到缺陷插槽即中） |
| 窗内首错出现时间（中位） | **17.3 秒**——大部分窗口过半就抓到 |

节奏图：

```
30min 周期:  ██ 2min 体检（CPU1→CPU2→CPU3→CPU4 轮流借）  ████████ 28min 业务独占全机 ████████
```

### 3.4 为什么 30 秒就"够准"——检测器是高压陷阱

测试让被测核在 30s 内陷入极高密度的"读-算-写-比对"循环：

- 每个线程反复扫描 1024 个数据槽：**3 次内存读取 → 轮换四种运算 → 背靠背双写回**
- 每扫完一遍，与开局用同一运算单元预计算好的**标准答案逐字节比对**（16KB memcmp）
- 30s 窗内单核约 **250 次全量比对、~77 万次读路径命中**——179 的读路径错误（概率约百万分之一每次读）无所遁形
- 出错即记录四要素：**哪个核（线程↔核一一对应）、第几秒（time-to-fail）、什么输入（随机种子）、错在哪**——一次事件完整可追溯

**命中率算术**：179 暴露期出错率 ~3.5 次/分钟 → 30s 窗期望 ~1.7 次 → **实测 12/12 窗窗有错**。窗口不能更短：15s 窗只覆盖 42% 的首错时刻，30s 是可靠性底线（实测 3 个窗口首错落在 33-39s，由框架的窗口自然过冲+同窗重试链兜住）。

### 3.5 为什么满载下测得出——关键实验依据

三构型对照实验（2026-10-25，同样满载背景）：

| 方案 | 检出结果 | 结论 |
|---|---|---|
| 单核独占（只测 179 一个核） | 330 秒 **0 检出** | 触发条件被负载门控关死 |
| 插槽共享（测试与业务分时共用） | 2×30s **0 检出** | 时序条件被并发负载打散 |
| **整插槽独占（现方案）** | **每窗必检出** | ✅ |

**要点**：检出条件是"**被测插槽安静**"，与全机负载无关——stress-ng 在其他三颗 CPU 上跑满完全不影响；且 179 的出错率在不同背景负载下稳定（跨背景鲁棒性已验证）。这就是"借整颗 CPU"而非"借几个核"的原因。

| 轮 | 窗内首错(秒) | 出错数 | | 轮 | 首错 | 出错数 |
|---|---|---|---|---|---|---|
| 1 | 17.1 | 2 | | 7 | 7.9 | 1 |

- **12/12 轮检出**，21 次出错全部锁定核 179；36 个干净插座窗**零误报**（每轮前三窗即特异性对照）
- stress-ng 全程零崩溃、零重启——业务侧对检测过程无感知
- 逐窗出错数 1-7 的波动即 179 的间歇性本身（爆发期窗口多错几个）

### 3.7 业务的代价（量化）

```
吞吐损失 1.815% = 每核被占 1.67%（30s/30min 机会成本）
                + 监控本底 0.12% + 边界开销
FARRON 自身计算 0.88% —— 从被预留的插槽里支取，不额外叠加在业务上
```

## 五、三形态实测总表（极限压测对照，证明"快而准"可扩展）

|---|---|---|---|
| 检出率 | 147/147 | 87/87 | **12/12** |
| 误报 | 0 | 0 | **0** |
| 业务吞吐损失 | 24.0% | 24.25% | **1.815%** |

| 检测延迟中位 | 18.5s | 15.9s | **17.3s** |

**论断**：检出能力只取决于"进入缺陷插槽的 30 秒窗"，与扫描频率无关——生产节奏与连续压测同为 100% 检出，代价相差 13 倍。

## 六、当前状态与边界

1. 检测协议三形态验证通过，生产部署形态一键可用（`farron/deploy_prod6h.sh`）
2. 集成缺口：全系统主控 `farron.py` 的测试执行器尚未接入插槽独占协议（合流中）
3. 温度轴衔接（另一数据包）：179 出错频率随本座温度升高而降（52°C ~13/min → 64°C ~1.8/min）——30s 窗设计在任何温度段均保持 100% 覆盖
4. 安全：98°C×2 看门狗全程在岗，温度控制器自动避让热边界
