# CORE179 流水线转发的理解与实践(2026-09-15)

依据:neon_rot_ldr_at_top_rowmajor 家族反汇编实录(`builddir/opendcdiag` objdump,
2026-09-15 抓取)+ 两世代实验的既有结论(记忆与 docs 可追溯数据)。
本文回答:"我们如何理解流水线转发、如何用它做实验、以及哪些话不能说"。

## 一、理解:转发是"比较+选择"电路,不是抽象概念

教科书层面:流水线把指令切成 IF/译码/执行/访存/写回,结果要到 WB 才进寄存器堆,
但后继指令在 EX 就要用——数据冒险。解法是在功能单元输入端加旁路多路器,
从流水寄存器里把在途结果直接抢过来,不等写回。

对本项目真正重要的是它的物理形态:转发网络 = 比较器(执行旁路里是源寄存器号
匹配;访存转发里是**地址**匹配)+ 多路器 + 跨越半个流水段的长线。它是时序
关键路径之一,也是"数据从哪来"的最终裁决点。由此两条:

1. 它有真实的物理面积和时序代价,不是免费的抽象;
2. 它分两个层面,本项目两个都碰过:
   - **执行旁路**(load/ALU 结果 → 下一条指令的操作数);
   - **访存转发**(在途 store 的数据按地址匹配直接喂给 load,不过 L1D)。

## 二、物化:热循环里每一条依赖边都是旁路边

基线 `neon_rot_ldr_at_top_rowmajor` 主循环体(objdump 实录,降序段 @`ca870`):

```asm
ldr  x1, [x19, #16]        ; ← scratch 基址重读(每元素)
add  x1, x1, x0            ;   地址合成
ldr  q0, [x1]              ; ① 顶部第3条ldr(scratch,结果不被消费)
ldr  x1, [x19]             ; ← srcA 基址重读
add  x1, x1, x0
ldr  q0, [x1]              ; ② 源A
ldr  x1, [x19, #8]         ; ← srcB 基址重读
add  x1, x1, x0
ldr  q1, [x1]              ; ③ 源B(②③=双源load)
and  w1, w2, #0x3          ; i%4 分派(编译器做成分支跳表)
cmp  / b.eq / b.ne
orr  v0.16b, v0.16b, v1.16b; ④ 轮换ALU:add v.2d / eor / and / orr 按i%4轮换
str  q0, [x21, x0]         ; ⑤ 背靠背双store(temp[i])
str  q0, [x20, x0]         ;   (dst[i])
sub  x0, x0, #0x10         ; 循环控制(降序)
cmn  / b.ne                ;   回跳
```

每元素 = **3×(基址重读+地址合成+`ldr q`) → 轮换 vALU → 背靠背 2×`str q`**。
依赖图上的转发边:

| 边 | 代码位置 | 转发含义 |
|---|---|---|
| ldr q0/q1(srcA/B)→ vALU | `neon_rot_ldr_at_top_rowmajor.cpp:101-110` | **load-to-use 0 拍旁路**——不旁路就得 stall |
| vALU → str q0 ×2 | `:112-113` | **ALU→store 0 拍旁路**,res 不过寄存器堆直达两条 store |
| 顶部 ldr(scratch) | `:98` | **无转发边**——结果架构上死亡(q0 随即被 srcA 覆盖),靠 asm volatile 才没被 DCE 删掉;作用是 load 端口占用/调度压力 |
| i%4 轮换 ALU | `:105` | 每个元素换一条旁路**路由**(加法器入口 ↔ 逻辑入口) |
| 升/降交替扫描 | `:94` | 循环接缝处 str→ldr 的邻接关系翻转 |

精确表述:热循环内**没有任何一条依赖边走寄存器堆往返**,全部是 0 拍边;
而三条 load 里只有两条形成转发边,第三条故意做成死的。
"三要素配方"(≥2源load+轮换ALU+紧时序)在转发视角下即:
**所有活边都必须 0 拍 + 每元素换旁路路由 + 一条死的 load 占端口**。

各格对骨架的唯一差异(objdump 核verify):

| 格 | 指令序列差异 |
|---|---|
| k5far / k5inter_rand | ②③ 的寻址换成 `src[2i]`/`src[2i+1]`(交错单缓冲),load/store/ALU 数不变 |
| k7p ×4 | **指令序列零差异**,只换内存填充(全0/全1/打标随机/0x55AA) |
| k3res | **指令序列零差异**,仅循环边界常数 0x400→0x1000(footprint 4×) |
| k4gap(零格) | ③④ 之间插 **8×nop** |
| k4bgap(零格) | ④⑤ 之间插 8×nop |
| k2pureload(零格) | 删 ⑤ 两条 `str q`,④ 后改 `eor v3.16b` 累加;校验移冷路径比对累加器 |

## 三、实践:两个世代的转发实验

**世代一(movbe/mrn_rmw,2026-08):显式打 store→load 转发窗口。**
同址 str→ldr 重读,nop 梯度曲线:0/1/2 nop 存活(~0.067 fail/min),
8/16/64 归零——"窗口 ≤2 拍"结论的出处。
代价:部分数据处于 SiliFuzz 污染窗口(2026-08-26 起),已标记降权。

**世代二(neon_rot 家族,2026-09):改打旁路邻接性。**
热循环里 store 写的 temp/dst 从不被 load 回来——所以 k2pureload(0 fail)
证明的是"**store 在场必要**",**不是**"store→load 转发必要"。这两句不可混。

四零格的干预与读法:

| 干预 | 破坏的边 | 结果 |
|---|---|---|
| k4gap:load→ALU 插 8 nop | load-to-use 旁路 | 0 fail |
| k4bgap:ALU→store 插 8 nop | ALU→store 旁路 | 0 fail |
| k2pureload:删 store | 上一条边 + store buffer 压力 | 0 fail |
| k7p_zero:数据全 0 | 数据门控(非转发边) | 0 fail |

工程纪律(血泪教训换来的):
- **干预必须在反汇编里核verify**——编译器会重排,源码加 nop ≠ 二进制里有 nop;
- 架构死亡的 load 必须 asm volatile,否则被 DCE(neon DCE 坑);
- dump 只能进冷分支,否则改掉热循环调度(30× 率塌缩教训);
- 变体间热循环须逐指令同构,否则不是单变量实验;
- 删临时测试永远手删注册行,不 git checkout(09-13 事故)。

## 四、认识论边界:能说的与不能说的

**不能说的**(既定教训:干预解耦不可能):插 nop 同时改了两件事——
是否走旁路路径,和时序余量。四零格只证明"所有边都必须 0 拍",
**不能**证明"缺陷骑在旁路通路上"。路径与时延在这类干预下绑死。

**反向也要诚实**:早年 objdump 对比(7 测试,2026-09-01)显示触发与不触发
测试的 forwarding 微操作**同构**——转发结构存在但不触发,即转发不充分。
所以转发是必要条件的侧写,不是充分条件,更不是故障位点。

**当前签名实际指向的层次**(读路径首轮 + K-cells 批次 2):
- 字段替换源 = 地址近邻(k5far:79/79 错位窗命中);
- mod-8 错位窗(头部族复现内核 mod-8 错位窗);
- got = exp ± X·(2³²−2¹⁶) 100% 符合,且 **eor 零例**;
- op 强偏置(orr 71% / and 23% / eor 5% / add 1%)。

其中"eor 零例"最有分量:若缺陷是旁路线上的位翻转,eor 的输出会同样出错——
它没有。损伤是"**拿错了哪个数据**(地址捕获/数据装配级)",
不是"数据在通路上被翻位"。叠加进位链形状的 ±X 签名,
矛头指向**装配/选择级**而非旁路网络本身。

## 五、一句话总结

对转发的实践不是"证明缺陷在转发网络里",而是把它当坐标系用:
四零格钉死"每条活边都必须 0 拍"的配方边界,
签名(eor 免疫、字段搬运、mod-8 错位窗)排除"缺陷在旁路数据线"候选。
转发是排除法和定位的地形图,不是已被指认的凶手。

# CORE179 硅失效诊断:从触发配方到关机根因(2026-09-17 汇报)

## 0. 背景与对象

- 平台:Kunpeng 920(ARMv8.1-A,AArch64),192 逻辑核,openEuler;诊断工具为 OpenDCDiag(开源 CPU 诊断框架)的 ARM64 移植版。
- 问题:单核(逻辑核 179)存在静默数据损坏(SDC)——load 指令低概率返回错误数据,无 MCE、无 RAS 报错,操作系统完全无感知。
- 判定手段:测试热循环对数据做 golden 比对,错误即 miscompare;全部实验在 192 全核并发下 30 分钟量级运行,错误计数为唯一失败块数。
- 事实基线:数以千计的失败样本中,**错误 100% 落在核 179**,其余 191 核零错误;排除 179 后长时间满载零失败。故障绑定该核的硅,属硬件缺陷。
- 179 的错误不限于用户态:内核态访存同样出错,由此衍生出两类更严重的显形——可恢复的内核 WARN 和致命 kernel panic(见 §5)。

## 1. "str+ldr(store→load 转发)是 SDC 触发的充分条件"是如何被否定的

早期主假说:SDC 出自 store→load 转发(forwarding)窗口——store 刚写入、紧随的 load 同址读回,数据从 store buffer 直接转发给 load,不过缓存阵列。支持证据是最初唯二触发的测试(movbe 57 次/30min、mrn_rmw 6 次/30min)都含同址 str→ldr。这个假说被三层实验逐级否定:

### 第一层:转发微操作完全同构,却不触发

对 22 个存量测试逐一反汇编热循环,对比"触发的 2 个"与"0 失败的 5 个":

| 测试 | store→load 微操作(反汇编实录) | 触发? |
|---|---|---|
| mrn_rmw | add;str [x0];ldr [x0] —— 同址同寄存器,背靠背 | **触发**(0.2 次/min) |
| mrn_nuke | add;str [x0];ldr [x0] —— **逐指令相同** | 0 失败 |
| mem_disambiguation | add;str [x6];ldr [x6] —— **逐指令相同** | 0 失败 |
| mrn_reloaded | strb;ldrb 同址背靠背(sub-word 转发) | 0 失败 |
| part_store_fwd_jit | JIT 生成的 str;ldr 背靠背 | 0 失败 |

**结论:store→load 转发微操作原样存在,仍零失败——转发本身不充分。**

### 第二层:补齐"2 源 load + ALU"后,时序仍是灭活开关

mrn_rmw 与 mrn_nuke 的差异是"2 源 load + ALU 依赖链 vs 1 源直通"。把 2 源 + ALU 移植到 mrn_pairs 骨架,做紧/松时序对照:

| 变体 | 内容 | 唯一差异 | 36min 失败数 |
|---|---|---|---|
| 紧时序版 | 2 源 load + 轮换 ALU + 同址 str→ldr 背靠背 | — | **46** |
| 松时序版 | 同上,但 store/load 按 8+8 展开,间隔拉开 7 条指令 | 时序 | **0** |

**松时序版拥有完整的"2源+ALU+同址背靠背 str→ldr",只因指令间隔拉开就归零。** 同时 1 源但紧时序的骨架也归零——所以任何单一要素都不充分,触发需要**"≥2 源 load + ALU 依赖链"与"紧时序(背靠背)"同时满足**。

### 第三层:reload(重读)的"存在性 vs 必要性"拆分

NEON 侧的三个变体给出著名的三点现象:

| 变体 | 热循环数据流 | 30min 失败数 |
|---|---|---|
| baseline | ALU → str temp → **同址** ldr temp → str dst | 26~33 |
| store_only | ALU → str temp → str dst(**无任何 ldr 重读**) | **14** |
| fwd_probe | ALU → str temp → **异址** ldr dst → str dst | **0** |

严格解读(经两轮技术评审修正):
- store_only 的 14 次失败证明**存在性命题**——"存在一种不含热循环重读的触发配置",即触发路径不止转发一条;但它相对 baseline 是四变量复合(依赖链步数、AGU 形态、指令条数、store 的数据流性质),不能证明机制同一;
- fwd_probe 的 0 同样是复合变量结果(重读值被丢弃,依赖链断裂),归为"功能等价改写即灭活"的存在性证据;
- **26/14/0 作为现象记录保留,机制归因悬置**——这三对比较没有一对是单变量,这正是后续做单变量拆分实验(§2)的动机。

**本节小结:str+ldr 只是必要条件侧写的一部分。充分性否定 = 同构转发零失败的反例群 + 时序灭活对照 + reload 三点拆分,三层证据叠加。**

## 2. "3 ldr + 轮换 ALU + 2 str"骨架是如何找到的

这个触发配方不是一次性设计出来的,而是五步实验收敛的结果:

### 第一步:三要素配方(09-01~02)

通过正向构造与跨骨架移植(§1 第二层)锁定三要素:
1. **≥2 源 load + 数据 ALU 依赖链**(store 的值须是两源经 ALU 加工的结果,非原值搬运);
2. **ALU 轮换/混合**——逐指令对照实验:固定单条 ALU(add/sub/eor/and 各 36min)全部 0 失败,轮换版触发。**起作用的是"轮换/混合"这个模式,不是特定指令**;
3. **紧时序**(关键访存指令背靠背,间隔≤2 拍)。

### 第二步:配方搬进 NEON 向量通路(09-03)

判别问题:配方是否绑定标量数据通路?设计上选 `uint64x2_t`(2×64b lane),使每条 lane 的运算语义与标量版完全同构,"执行通路从标量 ALU 换到 NEON 单元"成为唯一变量:

```c
a = srcA[i];  b = srcB[i];                 // 2 条 ldr q(双源)
switch (i%4) { vaddq/veorq/vandq/vorrq }    // 轮换 NEON ALU(64b lane)
str temp[i];  ldr temp[i];  str dst[i];     // 背靠背 str/ldr/str
```

结果:**33 次失败/30min(~1.1 次/min),全部核 179,首触发仅 11.6 秒**——是标量同构版的 1.7 倍。配方不绑定通路,且 NEON 版成为触发率最高的受控检测器。此步同时确立一条工程红线:NEON 的重读必须用内联汇编写(`asm volatile ldr`),编译器 intrinsic 会被直接消除——反汇编实证 store 后编译器直接复用寄存器,**load 根本不发出**。

### 第三步:lane 形状判定(09-03/04)

同宽度(16B)不同 lane 组织的对照:

| lane 形状 | 30min 失败数 |
|---|---|
| 2×64b | 26~33 |
| 4×32b | **0** |
| 16×8b | 2 |

**触发绑定 64-bit lane 数据通路本身,是阈值不是梯度**——4×32b 塌得比 16×8b 更彻底,排除"数据量计费"和"越宽越触发"两种解释。≥2 源阈值跨通路成立(NEON 1 源 = 0)。

### 第四步:拆分实验设计——3 ldr 骨架诞生(09-04)

为拆解 §1 第三层 fwd_probe 的 0("转发窗口关闭"还是"AGU 压力模式改变"),设计了位置对照探针:

```
neon_rot_ldr_at_top:
     ldr scratch[i]            ← 第三条 ldr 挪到迭代顶部(源 load 之前)
     a = srcA[i]; b = srcB[i]
     res = 轮换ALU(a, b)
     str temp[i]; str dst[i]
```

与 fwd_probe 同指令条数、同访存混合度(**3 ldr + 2 str**),唯一差异是第三条 ldr 的位置(两 str 之间 vs 迭代顶部)。**顶部第 3 条 ldr 的结果架构上死亡**(不被消费),从设计起就是 load 端口占用/调度压力探针——这就是 3ldr+轮换ALU+2str 骨架的出处。

### 第五步:从探针到稳定检测器(09-05~09-13)

- 稳定性战役:三变体 × 3 轮 30min 复测,rowmajor(升/降交替扫描)变体 3 轮共 **669 次失败(223/轮)**,**1019/1019 全部核 179**,失败在时间窗内均匀分布、跨 seed 独立——可复现的受控检测器;
- 附带发现:加 dump(落盘)冷分支使触发率塌缩 30 倍——**任何对热循环的改动都可能灭活**,检测与取证必须分离设计;
- 在此骨架上继续做单变量格点战役(§4),最终固化为 **7 个稳定有效的 SDC 测试用例**(1 基线 + 6 变体)。

**本节小结:3ldr+轮换ALU+2str = 三要素配方经 NEON 通路验证、lane 阈值判定、位置拆分设计五步收敛的产物;顶部第 3 条 ldr 是有意的端口压力设计。**

## 3. 多次 ldr / 多次 str 的梯度实验结果

### 3.1 源 load 数梯度(1→4 源)

mrn_nuke 骨架,只变源 load 数,其余逐字节不动,各 36min 全核:

| 源 load 数 | 失败/36min | 触发率 | 首失败 |
|---|---|---|---|
| 1 | 0 | 0 | — |
| **2** | **14** | ~0.39/min | — |
| 3 | 10 | ~0.28/min | 473s |
| 4 | 4 | ~0.11/min | 633s |

**非单调:2 源最高,3/4 源反而下降。**"≥2 源"是**阈值条件**而非"越多越好"——更多源拉长依赖链、增加指令数,反而扰动紧时序窗口。

### 3.2 多 store / 去 reload(AGU 压力实验)

标量四变体,各 30min:

| 变体 | 每元素指令流 | 失败数 |
|---|---|---|
| 2src | 2 源 load + {add,eor,and,orr} 轮换 + str/reload/str(**3 ldr + 2 str**) | **19** |
| 1src | 1 源 load + 同轮换 + str/reload/str | 0 |
| store_only | 2 源 + 轮换 + **2×str 无 reload**(**2 ldr + 2 str**) | **1** |
| unaligned | 2src 骨架 + 16B 槽位内旋转偏移(7/8 非对齐) | 0 |

NEON 侧对应:**双 str 无 reload = 14 次失败/30min**。

解读:
- **去掉所有 reload(纯双 store)仍能触发**(标量 1 次、NEON 14 次)——store→load 转发窗口**不是严格必要条件**,而是约 20 倍的强放大器;
- 轮换指令集可替换({add,sub,eor,and}→{add,eor,and,orr}仍触发)——再次确认"轮换模式"而非特定指令;
- 非对齐寻址 0 失败——布局敏感:改寻址方式即挪动时序窗口,灭活大概率是布局效应而非"非对齐免疫"。

### 3.3 零 store 反证(K-cells 批次,09-13)

`k2pureload` 变体:保留 2 源 load + 轮换 ALU + 顶部死 ldr,**删掉全部 store**,结果用 xor 累加器冷路径校验:

| 变体 | 热循环 | 30min 失败数 |
|---|---|---|
| 基线(3 ldr + 2 str) | 完整骨架 | 58 |
| **k2pureload(3 ldr + 0 str)** | 删 store,xor 累加 | **0** |

**store 在场是必要条件**——与 3.2 的"reload 非必要"合起来:触发配方需要 store,但不需要 store 被转发回 load。

### 3.4 时序间距反证(同批次)

| 变体 | 干预 | 失败数 |
|---|---|---|
| 基线 | load→ALU→str 零间隔 | 58 |
| k4gap | load→ALU 之间插 8 条 nop | **0** |
| k4bgap | ALU→str 之间插 8 条 nop | **0** |

**每一环都必须紧邻**:load 到消费、计算到 store,任何一端拉开都灭活。

### 3.5 复现性与率波动的最新数据(09-14/15)

7 个有效用例整夜逆序复跑(与首晚顺序完全相反),7/7 全部复现,失败仍全在 179:

| 用例 | 首晚(原序) | 复跑(逆序) |
|---|---|---|
| 基线 rowmajor | 58 | 18 |
| k5far(交错双源) | 37 | 16 |
| k5inter_rand(交错+随机) | 72 | 50 |
| k7p_rand(随机数据) | 78 | 34 |
| k7p_one(全 1 数据) | 42 | 8 |
| k7p_hiham(高汉明数据) | 44 | 9 |
| k3res(4×footprint) | 58 | 41 |
| **合计** | **389** | **176** |

- **用例间相对排序两晚一致**(交错+随机/随机/大足迹 > 基线/远距 > 全1/高汉明),负载特征对触发率的调制真实可复现;
- 绝对率整体塌缩到 45% 且 7/7 同向——变化系统性为真,但单晚绝对数不能当用例强度度量(逆序已排除执行顺序的解释,成因归结为机器状态的时间尺度波动,未定论);
- 方法论结论:**比较触发率须同时段配对,同晚内排序才有效**。

**本节小结:多 ldr——2 源是阈值,3/4 源降率,顶部第 3 条死 ldr 是端口压力;多 str——双 str 无 reload 仍触发(转发非必要),零 store 即灭活(store 必要);间距——全链紧邻缺一不可。**

## 4. 流水线转发研究的现状

### 4.1 触发骨架在转发视角下的精确形态

对 7 个有效用例逐一反汇编,热循环指令构成完全一致(3 条 `ldr q` → 轮换 vALU → 2 条 `str q`),依赖边全部是 0 拍旁路边:

| 依赖边 | 转发含义 |
|---|---|
| 源 ldr → vALU | **load-to-use 0 拍旁路**(不旁路即 stall) |
| vALU → str ×2 | **ALU→store 0 拍旁路**(结果不过寄存器堆直达 store) |
| 顶部第 3 条 ldr | **无转发边**(结果架构上死亡,纯 load 端口占用) |
| i%4 轮换 ALU | 每元素换一条旁路路由(加法器入口 ↔ 逻辑入口) |
| 升/降交替扫描 | 循环接缝处 str→ldr 邻接关系翻转 |

精确表述:**热循环内没有任何一条活依赖边走寄存器堆往返**;三条 load 中只有两条形成转发边,第三条故意做成死的。各用例的差异被严格限制在三个正交平面之一——寻址方式(交错/并行缓冲)、填充数据(全0/全1/随机/高汉明)、循环边界(足迹 4×)——指令序列在六个变体中逐指令同构或零差异。

### 4.2 数据内容门控(同一指令序列,只换数据)

| 数据模式 | 30min 失败数 |
|---|---|
| 全 0 | **0** |
| 全 1 | 42 |
| GPS 打标随机 | 78 |
| 0x55/0xAA 高汉明 | 44 |

**数据多样性是必要条件**(全 0 灭活),且随机数据最强——损伤不是均匀的位翻转,而是**模式敏感**的。

### 4.3 错误签名指向的层次(为什么我们认为缺陷不在转发数据线上)

对数百个失败样本做逐字段取证,四条独立证据:

1. **eor 零例**:错误字的差值 100% 符合 `got = expected ± X·(2³²−2¹⁶)` 的跨字段搬运形式(X 为小常数,集中于 0x80/0xc0 等低幅值);按出错运算分类,orr 占 71%、and 23%、eor **0 例**、add 1%。**如果缺陷是旁路线上的位翻转,eor 的输出会同样出错——它没有**;
2. **替换源 = 地址近邻**:错误字段的内容来自地址相邻的其他数据(交错布局下 79/79 命中错位窗),即"**拿错了数据**"而非"数据被改坏";
3. **mod-8 错位窗**:错误呈 8 字节粒度的窗口搬移,与内核态崩溃中观察到的错误地址形态同构;
4. **运算偏置与进位链形状**:orr/add/and 触发而 eor 免疫,±X 的常数形状指向装配/选择电路(含进位链结构),而非数据通路。

**综合判断:损伤位于地址捕获/数据装配级(决定"转发/取回哪个数据"的那一环),不是旁路传输线本身。**转发网络在本研究中是排除法的坐标系——用它钉死配方边界(§3.3/3.4 的零格)、再签名排除"缺陷在数据线"候选——而非已被指认的故障位点。

### 4.4 方法论边界(对外表述的严谨性)

- **干预解耦不可能**:插 nop 同时改变"是否走旁路路径"与"时序余量"两件事,零格只证明"所有活边必须 0 拍",不能证明"缺陷骑在旁路通路上";
- **转发不充分**(§1),转发亦非故障位点(§4.3)——它只是必要条件的侧写;
- **布局敏感是全局现象**:改寻址/改时序/增删指令/加 dump 分支都可能灭活,任何单变量结论必须以反汇编逐指令核对的同构性为前提。

## 5. 179 号核导致机器关机的原因

### 5.1 直接原因:12 次内核 panic 全部崩在同一条指令

对 12 次致命 panic(09-04 ~ 09-14,跨 6 天、跨 8 种不同受害进程)的 kdump 转储逐一分析:

- **崩溃点 12/12 完全一致**:`find_busiest_group+0x140`——内核调度器负载均衡路径上,读取 per-CPU runqueue 统计的那条 `ldr x23, [x27, #0x120]`(机器码 f9409377,全部样本一致);
- **寄存器交叉验证**:x27 + 0x120 精确等于每次的报错地址;
- **统一调用栈**:

```
find_busiest_group+0x140    ← 崩溃点(读 runqueue 负载统计)
load_balance+0x108
newidle_balance+0x198       ← CPU 即将转入空闲时触发
pick_next_task_fair → __schedule → schedule
(以下因进程而异: futex_wait / do_task_dead 等睡眠、退出路径)
```

- **报错地址形态**:全部是介于用户与内核地址范围之间的**非规范地址**——不是任何真实映射,是读到随机垃圾值再当指针解引用的产物。

### 5.2 机制链条:为什么"跑测试"会演变成"关机"

```
全核满载测试 (-n 191/192, 负载逼近核数)
    ↓
调度器把所有可运行进程摊到全部核 —— 包括与测试无关的系统守护进程
(pmdalinux / HeapHelper / mi-scavenger / rcu_sched / kworker ...)
    ↓
任何进程在 179 上睡眠/退出/让出 CPU 时,调度器为其做负载均衡
    ↓
find_busiest_group 在 179 上读 runqueue 统计 → 179 的 load 读路径
随机返回错值(与用户态 SDC 同源、同一坏硅)
    ↓
错值被当作指针/偏移解引用 → 非规范地址 → 翻译错误(level 0/2/3)
    ↓
Oops → kernel panic → kdump → 重启
```

关键更正:早期归因"守护进程在 179 上访存出错"不够准确——**守护进程只是乘客,司机是调度器**:不是受害者自己的访存错,而是调度器为它们计算负载时读错。受害进程的共性从来不是它们是什么负载,而是它们恰好在 179 上触发了调度器的负载均衡路径。

### 5.3 触发条件与防护手段(实测)

- **必要环境**:满载(负载均衡频繁触发)+ 179 在调度器内。实测 cpuset 排除 179 无效——它只约束测试自己的线程,拦不住 OS 把守护进程调度上 179(有 cpuset 排除后 pmdalinux 仍在 179 上报错的实录);
- **概率性**:满载不必然死,死时必然满载;历史死亡窗口为 run 启动后 1~16 分钟;
- **唯一可靠阻断:hotplug 下线 179**。下线后同等满载长时间存活;
- **旁证(180 对照)**:在相邻的 180 核上做对照——3 小时满载,179 上访客进程到访两千余次无一死亡、内核零错误,而同期用户态 SDC 113 次全部在 179 → **高流量零错误,错在核不在进程**。

### 5.4 同一根因的显形谱系

179 坏硅的读错误,按错值落点分三档,强度递增:

| 形态 | 表现 | 错值落点 |
|---|---|---|
| 用户态 SDC | 数据比对失败(全部核 179) | 被测 load 的返回值 |
| 可恢复警告 | spurious translation fault(45+ 例,CPU 全 179) | 可重试的页表遍历 |
| 致命崩溃 | Oops → panic → 重启(12 次,同指令) | runqueue 统计 → 坏指针解引用 |

即:**关机不是另一个故障,而是同一个读路径缺陷在内核敏感路径上的显形**。用户态 SDC 实验(§1-§4)定位的"load 读路径低概率出错"与内核态崩溃共享同一物理来源——这也解释了为什么 12 次崩溃横跨完全不同的受害进程(sftp-server/内存巡检守护/内核工作线程/测试线程自身)却崩在同一条调度器指令上。

### 5.5 处置建议

1. 生产处置:hotplug 下线 179(或 RAS 层面隔离),阻断调度;
2. 诊断侧:179 在线 + 全核满载即可复现用户态 SDC(7 个有效用例,~1-2 次/min 量级),作为硅失效的证据链;
3. 硬件侧:读路径(地址捕获/数据装配级,§4.3)为定位方向,建议结合 L1D ECC/RAS 计数器做零扰动佐证。

## 6. 总结(五句话)

1. **str+ldr 不充分**:转发微操作逐指令同构却零失败的反例群、补齐 2源+ALU 后被时序灭活的对照、reload 三点拆分——三层证据锁定;触发 = ≥2 源 load + 轮换 ALU + 紧时序,缺一不可。
2. **3ldr+轮换ALU+2str 骨架**:五步实验收敛的产物;顶部第 3 条 ldr 是有意的 load 端口压力设计;现固化为 7 个稳定有效的 SDC 检测用例,失败 100% 在 179。
3. **多 ldr / 多 str 的边界**:源数 2 是阈值(3/4 源降率);双 store 无 reload 仍触发(转发非必要),零 store 即灭活(store 必要);全链紧邻缺一不可。
4. **转发研究现状**:所有活依赖边必须 0 拍;但错误签名(eor 零例、跨字段搬运、mod-8 错位窗)指向地址捕获/数据装配级,而非旁路数据线——转发是定位的地形图,不是已被指认的凶手。
5. **关机根因**:12 次 panic 同指令崩于调度器 `find_busiest_group` 读 runqueue 统计——179 坏硅的读错误被调度路径放大成内核崩溃;满载把无关进程推上 179 是环境条件,hotplug 下线 179 是唯一可靠阻断。
